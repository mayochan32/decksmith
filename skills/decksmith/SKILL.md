# DeckSmith

原稿の意味とスタイルを読み、内容に合う紙面を設計する。Pythonは意味を解釈せず、JavaScriptは設計した要素を描画する。共通エンジンを使い、完成構図のプリセットや特定AIのSDKに依存しない。

## まず、画面で何を伝えるかを決める

新規制作・全体再設計では、原稿を読んだ直後に、各ページで聞き手が知りたいことと、その答えになる原稿の箇所を短く押さえる。その答えを文章・比較・関係・数値・画像の何で見せるかを決めてから配置する。

図や比較が答えになるページでは、先にその図や比較に必要な場所を配分し、見出しを添える。説明文を同じ枠へ分割するだけで理解しやすくなったと判断しない。同じ枠や位置に置く要素が本当に同格か、線が何の関係を示すかを確かめる。独立した条件を順序にしたり、対称な見た目のために異なる制約を落としたりしない。短い主張だけのページに図を足す必要もない。詳細は[内容と図解](references/communication-design.md)、複数ページは[構図と資料全体](references/composition-design.md)を使う。

全ページの詳細設計より先に、説明が難しい代表ページを試作する。[代表ページと反復](references/design-plan.md#代表ページと反復)に従い、同じ必須内容・スタイルから意味の見せ方が異なる2案を実際に描画する。まずプレビューだけから読める内容と迷う箇所を記録し、その後で原稿と照合する。採用するのは伝え方の原則であり、残りへ同じ配置を複製することではない。自分で選べる比較のために承認待ちを追加しない。

品質改善では文字切れの修正だけで完了しない。原稿中の具体例・差・接続が画面から読めるかを確かめ、画像・色・強調を理解に役立つ箇所へ使う。

見出しは題目、問い、原稿が支える要点から、そのページに合う形を選ぶ。良い題目を無理に結論へ変えない。改善時はcommunicationメモの要点と根拠を実際の見出し・図表へ結び付け、重複した説明を整理する。[見出しと強調の実装](references/communication-design.md#見出しと強調を画面へ反映する)に従い、見出し列だけの流れと、画面の強調箇所が同じ内容を伝えるかを確かめる。

枠どうしの受け渡し・条件分岐を編集可能な図で示す場合は、[接続線と条件ラベル](references/connector-routing.md)のconnectorで接続先を参照できる。文字を避ける経路とラベル位置を共通処理で組み立て、ノードの配置変更時も再計算する。図の関係と必要な条件は原稿から決める。関係を保てる図の案を、線の座標調整が難しいという理由だけで説明文へ置き換えない。自由曲線や軸などは従来のpathを使える。

## 作業範囲と開始設定

利用者の明示指示と既に得た承認を優先し、指定済みの内容や承認済みの同じ操作を再確認しない。題材・構成・スタイルは別々に扱う。参考資料は実際に見て、内容の根拠か見た目の参考かを区別する。

- 既存PPTXは[スタイル変換](references/restyle.md)で①スタイルのみ、②文章改善・配置固定、③文章・配置・ページ構成の再設計を扱う。①②では配置を維持し、③では元要素との対応を保存する。指定モードを勝手に変更しない。
- PDF入力は[PDF取り込み](references/pdf-input.md)も使い、元PDFと照合する。画像として保持した図表を編集可能な元データの復元とは説明しない。旧形式PPTは未対応。
- PORTABLE_GUIDE.mdとdecksmith.cmdがある同梱版はガイドとランチャーを優先し、Python・Node.jsを直接起動・追加導入しない。ブラウザー試用だけは[ブラウザー試験](references/browser-trial.md)を先に読み、クラウドMCPや別エンジンへ自動切替しない。

制作開始時は次を行う。内部ファイルを利用者に作らせない。

1. [制作設定](references/project-settings.md)でdecksmith.yamlとプロンプトを解決し、[制作補助](references/workflow.md#開始時の設定)のprepareを使う。言語・文字量・画像方針・画像計画・保存先を反映する。元設定を上書きしない。
2. [実行環境](references/host-runtime.md)に従いdoctorで描画方式・依存・フォントを確認する。scripts/version.pyまたはdoctor.pyの実測版番号で「DeckSmith vX.Y.Zで作成します」と表示する。
3. 確定サイズ、通信モード、Web検索・外部サービスの承認条件、組み込み画像生成の許可と利用可否、ローカル処理の可否を表示する。「原稿・画像・プレビューは利用中のAIサービスへ送信され得る」と説明する。privacyの既定はrestricted。全モードで外部操作には目的・利用先・送信情報を示した人間の事前承認が必要で、restrictedでは制限の例外とも明示する。設定や画像計画から通信の承認を推測しない。

サイズ未指定は横長16:9・1920×1080px。別指定は優先してscene.canvasへ記録する。標準はmy-presentations/setting/に入力と制作ファイル、同列のoutput/に納品物。明示の保存先は維持する。雛形が必要な場合だけassets/decksmith.yamlまたはproject_init.pyを使う。nullから素材や内容を推測しない。

## 設計を保存して描画する

1. 原稿から表示する主張・条件・必須文字と話者ノートを分け、structure.yamlとtext-plan.mdへ記録する。適用対象・成立条件・例外は原稿の文もtext-plan.mdに残し、表示文への短縮で範囲を広げない。必須語の存在だけで条件保持を満たすとは判断しない。text.amountとページ別指定を適用し、画面掲載必須の内容をノートへ逃がさない。[制作補助](references/workflow.md#原稿の必須内容を先に固定)のfreeze-contentでsceneより先に原稿由来のcontent-contract.jsonを保存する。表・グラフは[ネイティブ表・グラフ](references/native-evidence.md)に従い全項目・値・単位・条件をevidenceへ別に固定する。sceneから検査基準を逆生成しない。変更時は原文・変更後・理由・原稿上の根拠を残す。
2. 元のstyle.yamlを独自キーや日本語記述のまま保持する。[スタイル解釈](references/style-system.md)で末端値を要件台帳へ対応づけ、[デザイン方針](references/design-plan.md)に主役・読み順・構図・書体・素材・達成状態を記録する。未対応・素材不足はblocked/asset_pendingとし、非該当に偽装しない。元ファイルのSHA-256をsceneへ記録し、原稿やYAMLの変更時は再解釈する。指紋だけ更新して流用しない。
3. 代表ページを比較してから残りを設計する。[シーン仕様](references/deck-spec.md)で位置・寸法・重なり・回転・文字組みをscene.yamlへ保存する。文字のまとまりと図形の寸法には[配置バランス](references/layout-balance.md)を必要な箇所に使う。文字・正確なラベル・線・数値は編集可能に保つ。完成ページ全体を画像にして編集可能とは説明しない。
4. 画像を使う場合は[画像素材](references/image-assets.md)と制作設定の画像計画を適用する。必要画像だけ先に作り、実物を見て配置する。事実を示す画像は提供資料を使い、生成画像に本文や数値を焼き込まない。provided_onlyで生成しない。images.plan=confirmでは承認前に生成・取得・加工・PPTX生成をしない。必要画像を用意できなければ理由と対象を示し、画像なし再配置か編集可能なプロンプト付き四角の代案を確認する。無回答で省略・図解代替・外部サービスへ切り替えない。開発チャットやリポジトリのartifacts/を素材にしない。
5. scripts/create_deck.pyを実行する。解決済み設定を--configで渡す。

   ```bash
   python3 <skill-directory>/scripts/create_deck.py \
     --scene <project>/scene.yaml --style <project>/style.yaml \
     --structure <project>/structure.yaml --config <project>/decksmith.resolved.yaml \
     --output <project>/../output/deck.pptx
   ```

   <project>はsettingフォルダー。既存出力を上書きせず、修正は--next-outputで別名生成する。rendererはlibreoffice（既定）、powerpoint（Windows）、none。noneは利用者の明示指定時のみ使い、変換失敗を理由に切り替えない。ホスト専用の操作記録はホスト側で行う。

## 画面と原稿の両方を確認して渡す

[品質検証](references/quality-gates.md)で全ページのPNGを見て、理解できる内容・判読性・スタイルを別々に確認する。図の関係・条件と表の全項目は原稿へ戻って照合する。設計意図や機械検査の成功だけを根拠に見た目を合格にしない。

必須語がネイティブ文字として残っていても、別の文字や図形に隠れる、背景と同化する場合は内容が伝わらない。文字同士の衝突・遮蔽・既知の背景との色の対比の検査を手がかりに直し、画像上や回転文字などの未測定箇所も実物で読む。警告を消すために文字を削ったり一律縮小したりせず、配置・描画順序・配色を原稿と指定スタイルの範囲で見直す。

review.jsonを実物と一致させ、scripts/review_deck.py --output <pptx>（同梱版はreview --project <project> --output <pptx>）を実行する。PPTXとPNGの対応、原稿基準、通信記録、承認を照合する。noneは「PPTX生成済み・見た目未確認」を維持する。

[ページ別の説明資料](references/design-notes.md)を最終版に合わせ、同名の.design-notes.mdとしてPPTXの横へ保存する。利用者が不要と明示した場合のみ省略する。DELIVERY.mdへ納品対象を明記し、最終PPTX・必要なPDF・説明資料を案内する。修正比較には[compare --board](references/workflow.md#修正後の比較・納品)を使える。出力フォルダーや旧版を削除しない。
