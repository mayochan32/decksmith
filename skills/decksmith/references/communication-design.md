# 内容から図解と読み順を決める

座標を決める前と、描画後のレビューで使う判断基準。完成レイアウトのカタログではない。利用者の原稿・ページ数・文字量・スタイルを優先し、このガイドのために情報を削除したり、すべてのページを図解化したりしない。

## 先に伝える関係を確かめる

各ページで、聞き手の問いと、原稿が実際に答えられることを一文ずつ考える。構成指定がある場合はその順序を保つ。結論が未確定なら「何が未確定か」を伝え、強い見出しを作るために断定しない。

図解が有効なページでは、要素を取り出し、**何と何が、どう関係するか**を原稿に照らす。その後に表現を選ぶ。項目数や見た目だけで図を選ばない。以下は意味を見分ける問いであり、選べる図の限定リストではない。

| 原稿から確認すること | 表現の候補と確認点 | 避ける誤読 |
| --- | --- | --- |
| 独立した項目か | 一覧・まとまり。等価な項目は同程度に扱う | 並べただけの項目に矢印を加えて手順にする |
| 同じ対象を同じ観点で比べるか | 対応する行・基準・単位を揃えた比較 | 片側だけ条件を省き、優位に見せる |
| 時間や処理が進むか | 順序・始点・終点を示す。期間も重要なら尺度を持つ時間軸 | 左右の順序を因果関係と断定する |
| 元の段階へ実際に戻るか | 戻り先と条件のわかる循環・フィードバック | 円形配置だけで循環を意味させる |
| 分配・統合・選別なのか | 向きと接続先、入力・出力・条件を示す | 分岐と合流、集約と因果を混同する |
| 所属・支持・順位のどれか | 関係を明記した階層・包含。面積が数量かも区別 | 協力関係を上下関係にする。段階を量の大小に見せる |
| 共通部分が実際にあるか | 重なりの意味を説明できる交差・集合 | 関連があるだけの概念をベン図にする |
| 二つの軸で位置を決められるか | 軸の意味・尺度・配置根拠を持つ座標図 | 4項目だから四象限にする。右上を無条件に優位にする |
| 中心と周囲、複数主体が関わるか | 中心の役割・線の意味・方向を区別した関係図 | 全結合や双方向の矢印を根拠なく追加する |
| 数値の何を読むか | 比較・推移・構成比など目的とデータに合うグラフ | 都合のよい範囲・面積・立体効果で差を誇張する |

関係がない、短い主張だけで十分、画像そのものが証拠、といった場合は図解を選ばなくてよい。写真・表・引用・文章にも役割がある。ネイティブ表・グラフが必要な場合の実装条件はSKILL.mdに従う。

最初に把握するまとまりを少なくすると見通しを作りやすい。ただし「2〜4項目」は整理の検討材料であって上限ではない。6つの独立した必須条件を、見た目の都合で3つへ削ったり、意味のない上位分類を作ったりしない。まとめるなら原稿中の共通性を根拠にし、各項目への対応を残す。

## 図の意味を、スタイルに合う画面へ変える

[構図の選択と資料全体の流れ](composition-design.md)に従い、主役の配置から画面を組む。以下の「主役」は大見出しと同義ではない。

- **主役**：最初に理解すべき主張・差分・関係を目立たせる。必ず一つの図形だけを大きくする必要はなく、比較の一組も主役になる。章番号や装飾が主張に勝っていないかを見る。
- **読み順**：主役、根拠、条件を追える配置にする。矢印は視線誘導の飾りではなく、内容上の方向を表す。静止画でも関係を理解できるようにする。
- **揃えと余白**：関連するラベルや比較対象の基準線を揃え、まとまりの間に区切りを作る。字面の揃いも画像で確認する。全面対称・全要素同間隔を強制しない。
- **色の役割**：基調・補助・強調の役割を決め、同じ意味の色をページ間で維持する。利用者の多色・モノクロ等の指定を尊重し、色だけに意味を預けない。
- **統一と変化**：書体の役割、線、色、素材の扱いに共通性を持たせる。内容が比較から手順に変われば配置は変えてよい。同じカード列の反復で統一を代用しない。
- **数値と証拠**：注目箇所を強調しても、母数・期間・単位・条件・出典を隠さない。概念図の位置や大きさを測定値のように見せない。イメージ写真を実績の証拠にしない。

## 設計とレビューに短く記録する

design-plan.yamlの各slidesに、既存のfocal_reason/compositionと重複しない範囲で、自由記述のcommunicationメモを加える。機械が意味を検証するスキーマではない。

```yaml
communication:
  audience_question: 誰が次の担当を決めるのか
  takeaway: 受付が担当を決め、未解決の案件だけが受付へ戻る
  relationship: 受付から担当への割当と、未解決時のフィードバック
  source_basis: 原稿「運用案」の担当と差し戻し条件
  representation_reason: 矢印に条件を添え、通常経路と戻りを区別する
  reading_order: 主張 → 受付と担当 → 戻る条件
  avoid_misreading: 解決済みの案件まで循環させない
```

図解不要ならrelationshipを「関係図なし」とし、理由を一文で十分。記録を埋めるために関係や項目を作らない。

描画後は原稿を先に読み、次にプレビューだけから主張・関係・条件を説明できるか確認する。説明できない場合は図の選択へ戻り、装飾追加だけで直さない。

| 確認 | 実際に記録する証拠の例 |
| --- | --- |
| 意味 | 「未解決」の矢印だけが受付に戻り、完了への経路と区別できる |
| 主役・読み順 | 比較対象の対応行を横に追え、差分のあとに条件が読める |
| 判読性・揃え | 日本語ラベルが線から離れ、同じ役割の開始位置が揃っている |
| スタイル | 原稿指定の明朝見出しとモノクロの線を保ち、一般的な青いカードへ置換していない |
| 資料全体 | タイトル列から問いと答えのつながりが追え、同じ項目の色や呼称が途中で変わらない |

review.jsonの既存content/legibility/styleのevidenceへ書く。意味の誤りはcontent、読みにくさはlegibility、指定表現との違いはstyleで区別する。採点の平均で内容の欠落や誤った関係を相殺しない。
