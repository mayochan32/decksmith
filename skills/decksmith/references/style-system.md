# スタイルの解釈と設計

スタイル名や特定の英単語で分岐しない。利用者が渡したYAMLを原文のまま保持し、AIが全体を解釈する。例示のカタログはその依頼の表現意図として読む。すべてのカタログ項目を短い資料に詰め込む必要はないが、選ばなかったものは理由を記録する。

## 解釈結果

元YAMLの各末端値にJSON Pointerでsourceを付ける。キーの/は~1、~は~0にエスケープする。配列は/0などで参照する。台帳のinterpretationへ具体的な実現方法を書く。implementedにはスライドIDまたはslideID/elementIDのtargetsを付ける。not_applicableには理由が必要。単に実現が難しい指定をnot_applicableにしない。

元のYAMLと台帳の対応は自動検査できるが、その解釈が正しいかはAIが視覚的に照合する。台帳の自己申告を品質保証にしない。Style名などメタデータはnot_applicableでよい。陰影禁止のような全体ルールは適用ページをtargetsにする。

## ページ設計

主張と素材から、視線の入口、文字の大小、写真の主題、関係を示す図、余白を決める。配置比率もページごとに設計する。構図を固定カテゴリへ押し込めない。利用者のYAMLに中央配置や分割が指定された場合はその指示を反映する。

書体は見出しと本文の役割ごとに選び、実環境で利用可能か確認する。日本語と欧文の対応も確認する。代替が必要なら相違を記録する。巨大文字を指定されても情報を黙って省略しない。

素材生成はページ設計の後に行う。画像は装飾か説明か証拠かを区別し、説明画像はスライドの内容に合わせる。背景・切り抜き・テクスチャを別素材にすると、編集可能な文字との重なりを制御できる。全素材はその資料内で完結させる。

未知の表現を既存の構図へ置換しない。sceneで表現できない要素は未対応として扱い、必要な汎用描画能力を拡張して実証する。
