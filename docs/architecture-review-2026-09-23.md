# DeckSmith設計の再評価

## 結論

目的（利用者が与える未知のスタイルYAMLを解釈し、配布先で高品質なPPTXを生成する）は妥当だが、現行のキーワード分類と固定構図ビルダーでは達成できない。プリセットファイル削除だけでは解消していない。意味解釈・ページ設計をホストのAIへ移し、描画と検証を決定的な処理として分離する。

これは調査結果と変更提案であり、新方式の実装完了を示すものではない。今回、既存の生成コードは変更していない。

## 確認した問題

- `compile_spec.py:layout_variant`が文章のキーワードから固定バリアントを選ぶ。`build_deck.mjs`が各バリアントを固定座標で描く。中央配置や比較カードなどの完成構図は、文字・線・図形と同じ意味での汎用描画プリミティブではない。
- ハーフトーン表紙のDesignを「右下の小さいタイトル、中央は空白、副題の箱なし」に変えても、記録用Design文字列を除いたコンパイル結果は完全に一致した。ビルダーはDesign文字列を解釈しない。
- 利用者の元の配色キー（Base / Main Color / Contrast / Text Color）を与えると、accentが赤ではなく背景と同じクリーム色になった。保存されたサンプルYAMLではキーがEmphasisへ変更されており、入力形式の問題を隠している。
- Dot Matrix Chart、Grid Planner Data、Industrial Timelineはstandardへ落ちる。framed-galleryとtechnical-diagramは分類名があっても専用の描画処理がない。
- art_directionは確認用台帳へ保存されるが、被写体位置、文字安全域、重なりの指定として描画に使われない。treatment、grayscaleなども描画段階で実行されない。
- 見出しと本文のフォント役割が単一familyへ潰れる。文字サイズも少数の既定値へ縮約される。
- SWISS HALFTONE / 01というスタイル固有文字列がビルダーに残る。円形工程では5項目目以降をsliceで黙って捨てる。
- 黒板サンプルには`artifacts/blackboard/build/build_blackboard.mjs`という専用の制作コードが存在する。そこで得た品質は、配布プラグインの経路による再現性の証明にならない。
- 12件の既存テストは成功したが、上記の問題は検出されない。入力整合性とフィールド保持のテストが中心で、画像としての品質・意味的な指定遵守を保証しない。
- Presentationsの検出は内部ファイル名と旧配置候補に依存する。配布先での機能検出・実行検証は別途必要。

## 参考資料から残すべき学び

既存のPDFレンダリングから、赤系・ハーフトーン系・黒板系の各表紙と説明ページを再確認した。Google Drive上の原本は今回の環境では読み取りが拒否されたため、以前に保存されたPNGを使用した。今回、全ページ再評価はしていない。

共通して重要なのは、題材と表現が一体になっている点である。能面そのものを網点で構成する、VRと能面と脳の絵を使って問いを囲む、矛盾する感情を色付きの円で接続する、といった内容固有の設計がある。色・背景・構図名だけの抽出では失われる。

赤系では文字の占有率・改行・文中の色分け、ハーフトーン系では題材そのものの網点化・技術図解、黒板系では図と文字と背景の質感の統一が重要。これらを特定スタイルの実装分岐として保存せず、入力仕様から導いた要件と評価項目として扱う。

## 推奨する生成経路

1. 元のYAMLを保持し、ホストのAIが意味を読む。独自キー、自然言語、日本語、禁止事項を含め、特定のキー名や英単語の列挙に閉じない。
2. 要件台帳を作る。各指定にID、元記述、解釈、必須/任意、実現方法、検査方法を記録する。未解決項目を黙って既定値へ落とさない。
3. 内容とスタイルから各ページを設計する。主張、情報量、視線の順番、文字の占有率、画像の意味、素材、前後関係を具体化する。カタログは利用者が渡す指示として扱い、プラグイン内の構図一覧へ変換する制約は設けない。
4. 資料固有のシーン記述を生成する。テキスト（部分強調を含む）、図形、線/パス、画像、グループ、表、グラフに、位置・寸法・回転・順序・書体・色を指定する。利用者にこの内部形式を書かせない。
5. 必要な画像・質感を、そのページの配置と内容に合わせて生成する。背景、切り抜き、装飾、図解の部品を分ける。本文・数値・正確なラベル・関係線は編集可能な要素として保持する。
6. スタイル名を知らない描画層がシーンをPPTXへ変換する。未対応の要素は明確に報告し、近い構図への置換や内容の切り捨てで成功扱いしない。
7. 実際に描画した各ページをAIが元YAML・要件台帳・参考資料と照合する。文字切れ等の構造検査と、美観・忠実度の検査を分離する。修正して再描画し、残った制約を記録する。

自由な表現を過小な中間形式で再び制限しないこと。固定レイアウトの列挙は廃止するが、通常の図形・パス・画像・文字組みの支援関数は再利用できる。特殊な装飾はベクターや画像素材として表現する。全文字を画像化したPPTXを、編集可能な完成品として扱わない。

## 配布と品質検証

配布物に含めるのは、AIが読む生成・評価手順、シーン仕様、描画支援、素材処理、検証処理。チャット履歴、開発者のローカル素材、個別資料用ビルダーへの依存を除く。ホストの画像生成・PPTX描画・フォントの利用可否を開始時に検出し、利用できない機能を明示する。

同じ短い題材を、既存3スタイルと未使用のスタイルで作る。後者には日本語記述や独自の項目名も含める。コード変更を挟まず、配布用プラグインだけを別の作業ディレクトリへ置いた状態で生成する。過去の成功サンプルは評価資料であり、実行時のプリセットにしない。

合格条件は、全内容の保持、指定配色と書体役割、指定した配置の変化、題材に合う画像、主要文字/数値の編集可能性、画像検査による忠実度、配布先での再現性。特に、配置や色の指定を変えたとき、出力も対応して変わることを確認する。実行成功だけを品質合格としない。

## 置き換えの優先順

最初に固定構図への分類を外した最小の描画経路を作り、表紙・説明図・比較の3ページで、同じ内容を異なるスタイルへ変える縦断検証を行う。代表ページで品質を実証してから全体へ展開する。

残すものは、題材/構成/スタイルの入力分離、PPTX書き出し、構造検査、プレビュー生成、出典記録。置き換えるものは、キーワード式スタイルコンパイラ、固定座標バリアントの分岐、分類できない指定の黙認、サンプル専用制作経路。モデル変更だけで解決したとは判断しない。
